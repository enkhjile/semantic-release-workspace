# Prereleases and release branches

Use semantic-release’s normalized release, maintenance and prerelease branches. Keep the workspace batch tag format. A branch owns its pending journal, while completed plans remain available as history to descendant branches. Old single-branch journals remain readable. Prepared manifests and retained artifacts have a branch/channel scope for multi-branch releases.

Per-package baselines come from completed ancestor releases (or existing package tags). Prerelease branches admit their own prerelease identifier and stable versions; stable and maintenance branches exclude prereleases. Dependency-triggered bumps use the same version policy. npm dist-tags follow semantic-release channels, with numeric channels mapped to release-<channel>. Cargo channels are represented by SemVer and Git history, since Cargo has no dist-tags.

Stable-to-stable promotion uses addChannel. Verify the retained artifact and registry checksum, then add the npm channel without publishing again. A durable write-ahead promotion journal recovers after semantic-release has recorded the batch channel but the plugin operation fails. Dry runs never write journals, tags, manifests, registry versions, identities or channels. Pending plans and destinations remain frozen across fresh clones.

The coordinator version is independently versioned; branch ranges on semantic-release batch versions do not imply every package has that numeric version. Package conflicts and maintenance boundaries are checked separately.

References: semantic-release.org/foundation/workflow-configuration/, semantic-release.org/developer-guide/plugin/, doc.rust-lang.org/cargo/reference/specifying-dependencies.html, github.com/npm/cli/blob/latest/lib/commands/dist-tag.js, github.com/npm/cli/blob/latest/lib/utils/oidc.js.

## Recovery and compatibility decisions

- Stable branches share coordinator version allocation. A pending stable batch blocks new batches and promotions on other stable branches, including unrelated packages, until recovery. Prerelease identifiers have separate counters. Only completed/adopted higher releases receive the ancestor exemption when checking package bounds.
- Detect pending state at the old journal ref when branch ordering changes its primary role; configuration changes cannot hide the reservation.
- Select dependency projections from the newest ancestor plan carrying a package baseline, including unchanged packages and legacy journals without archives. Restrict carriers to stable history and the current prerelease identifier so dev-only prerelease ranges do not leak into stable plans.
- Keep new history/channel refs outside semantic-release's own Git-note prefix, which its channel parser scans. Retain the existing primary journal for compatibility.
- semantic-release 25 cannot reliably recover dotted or numeric-only prerelease identifiers. Reject those forms before writes; allow single identifiers such as beta-test.

- Preserve core 25 commit-level channel lookup in a plugin-owned, lexically earlier notes ref, semantic-release-0-workspace. Merge canonical core tag channels at the source commit before tagging and after addChannel. This avoids root-journal shadowing and preserves independent prerelease counters when multiple branch tags share a source commit. Normal remote pushes retain conflict rejection; dry runs never write this metadata. Repair unreadable legacy root channel notes during verification, then require a fresh invocation to reload core’s already-loaded tags. Preserve the frozen journal and never republish during repair; dry runs only report EWORKSPACECHANNELRETRY.
