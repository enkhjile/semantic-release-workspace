# Package attribution and version planning

Implement the authorized planning milestone for the Node 24+ semantic-release plugin. Keep existing batch tags, dry runs, completion tracking, and fresh-clone retries. No manifest writes, package tags, registry operations, or publishing yet.

Attribute each non-skipped commit by its changed paths against its first parent, including both sides of renames/deletions and root commits. The deepest discovered package directory owns a path; packages of different ecosystems at the same directory both own it. Commit scopes do not override paths. Unowned files are ignored unless matched by the optional repository-relative `sharedFiles` globs, which attribute the commit to every package. Empty inventory retains the lifecycle proof behavior.

Analyze attributed commits with the real Conventional Commit analyzer. Baselines prefer completed journal versions and newer reachable stable `npm/<name>@<version>` or `cargo/<name>@<version>` tags. Otherwise use a stable manifest version (Cargo workspace inheritance supported); missing versions start at 1.0.0 on their first release. Existing baselines increment by the strongest major/minor/patch signal. Keep each package’s history since its own completed version or tag; another package’s batch must not consume unreleased commits. Ignore history already covered by that package baseline. Reject invalid/prerelease baselines rather than guessing.

Build separate npm and Cargo internal dependency graphs. npm supports semver, workspace protocols/aliases, and local file/link references. Registry aliases, git/URL dependencies, and incompatible registry ranges are external. Cargo links path dependencies, including renamed, inherited, target-specific, build/dev, and legacy table aliases; registry-only dependencies are external. Validate explicit local references and unsupported internal ranges. Cargo bare requirements mean caret compatibility, and comma-separated comparators mean conjunction.

Coordinate releases to a fixed point. An incompatible runtime/build/optional range causes a patch release of its dependent, unless a stronger direct signal exists. Incompatible npm peer ranges cause a major. Development-only changes appear in the plan but do not force dependent releases. Workspace/file/link and Cargo path-only references track the new local version. Keep private packages in planning, marked non-publishable. Emit dependency field locations and proposed ranges. Produce dependency-first strongly connected groups, allowing npm cycles to settle without repeated increments. Inherited Cargo versions are planned independently; a later writer must materialize differing versions in member manifests.

Expose a deterministic JSON plan in release notes and the publish hook result. Journal schema 2 stores completed package baselines, identity-bound projected dependency ranges, and the exact pending plan. Still-unapplied projected ranges remain visible in subsequent plans without triggering extra releases. Retrying the same source/config reuses the same package versions even if the batch attempt tag changes. Detect changed plans on retry. Read schema 1 journals for migration. Corrupt schema 2 state fails before tagging. Completing a planning batch advances planned baselines, not evidence of registry publication.

Verify real Git histories and semantic-release subprocesses with local bare remotes, including initial releases, per-package histories, nested and cross-package changes, root/shared paths, renames/deletions, dependency chains/cycles, npm/Cargo range differences, private packages, unchanged runs, dry runs, retry, and damaged journals. Use exact stable dependency pins; preserve current tooling versions.
